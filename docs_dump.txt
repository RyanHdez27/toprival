La complejidad adicional de:
API Gateway
Service Discovery
Message Brokers
Distributed Transactions
Observability distribuida

10. Autenticación de dos factores
Aquí haría una modificación respecto a tu idea inicial.
No intentaría que el usuario tenga simultáneamente:

SMS

como métodos obligatorios.
Lo correcto es:
2FA
 │
 ├── TOTP
 │    └── Google Authenticator
 │
 ├── Email OTP
 │
 └── SMS OTP
El usuario podrá configurar uno o más métodos.
Mi recomendación
Método principal: TOTP
Por ejemplo:
Google Authenticator
Microsoft Authenticator
Authy
El usuario escanea:
QR

Authenticator
 ↓
Código de 6 dígitos
Backup
Email OTP.

Lo dejaría como método opcional/futuro porque tiene mayor costo operativo y dependencia de proveedor.

22. Algoritmo de generación
Supongamos:
6 participantes
Calculamos:
nextPowerOfTwo(6) = 8
Entonces:
8 - 6 = 2 BYES
Generamos:
Round 1
4 matches
Round 2
2 matches
Final
1 match
Total:
7 matches
La fórmula:
matches = bracketSize - 1
Por ejemplo:
8 participantes → 7 matches
16 participantes → 15 matches
32 participantes → 31 matches
23. Algoritmo de conexión
Cada partido tendrá:
next_match_id
next_match_slot
Ejemplo:
M1 ─────┐
        ├── M5
M2 ─────┘
M3 ─────┐
        ├── M6
M4 ─────┘
M5 ─────┐
        ├── FINAL
M6 ─────┘
Base:
M1 → M5 SLOT 1
M2 → M5 SLOT 2
M3 → M6 SLOT 1
M4 → M6 SLOT 2
M5 → FINAL SLOT 1
M6 → FINAL SLOT 2
24. BYE
Cuando:
MATCH
slot 1 = Participant A
slot 2 = NULL
el sistema ejecuta:
completion_type = BYE
status = COMPLETED
winner = Participant A
y automáticamente:
advanceWinner()
25. Avance automático
La función conceptual:
advanceWinner(matchId)
hará:
1. Buscar match.
2. Verificar que esté COMPLETED.
3. Obtener winner.
4. Verificar next_match_id.
5. Obtener next_match_slot.
6. Verificar que slot esté vacío.
7. Insertar participante.
8. Evaluar si el siguiente match tiene BYE.
9. Si corresponde → avanzar nuevamente.
10. Si no → esperar al segundo participante.
Esto permite una cadena como:
BYE
 ↓
MATCH COMPLETED
 ↓
BYE
 ↓
MATCH COMPLETED
 ↓
FINAL
sin intervención administrativa.
26. Transacciones
Esto es extremadamente importante.
La finalización de un partido debe ser:
@Transactional
porque necesitamos actualizar simultáneamente:
MATCH
MATCH_RESULT
MATCH_PARTICIPANT
NEXT_MATCH
TOURNAMENT_PARTICIPANT
RANKING
USER_COMPETITIVE_STATS
Si falla una operación:
ROLLBACK
y no queda el torneo en un estado inconsistente.
27. Concurrencia del último cupo
Aquí utilizaría PostgreSQL junto con una transacción.
Conceptualmente:
BEGIN
SELECT tournament
FOR UPDATE
verificar cupos
registrar solicitudes
resolver prioridad
confirmar participante
COMMIT
El punto importante es que el backend debe bloquear la fila relevante del torneo mientras se resuelve la asignación.
No confiaría únicamente en:
SELECT current_participants
porque dos peticiones simultáneas podrían observar el mismo cupo.

35. Primera etapa de escalamiento
Cuando aumenten los usuarios:
API
 ├── Instance 1
 ├── Instance 2
 └── Instance 3
Todas ejecutan el mismo backend.
Necesitaremos:
Load Balancer
+
Redis
+
PostgreSQL
El backend debe ser stateless.
Por eso no guardaremos sesiones críticas únicamente en memoria del servidor.
36. Segunda etapa
Si TopRival empieza a recibir mucho tráfico:
                     API
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
   Tournament     Identity      Community
     Module        Module          Module
Todavía pueden permanecer dentro del mismo repositorio/aplicación.
37. Tercera etapa
Si el motor competitivo se vuelve muy demandante:

             │
             ▼

             ├── Brackets

3. CASOS DE USO
CU-01 — Registrar usuario
Actor principal
Visitante.
Objetivo
Crear una cuenta para utilizar TopRival.
Precondiciones
El usuario no debe tener una cuenta registrada con el mismo correo.
El nickname no debe estar ocupado.
Flujo principal
1. El visitante accede al formulario de registro.
2. Ingresa correo electrónico.
3. Ingresa nickname.
4. Ingresa contraseña.
5. Confirma la contraseña.
6. Envía el formulario.
7. El sistema valida la información.
8. El sistema crea la cuenta.
9. El sistema solicita verificar el correo.
10. El usuario verifica su correo.
11. La cuenta queda habilitada.
Flujos alternativos
Correo existente
Correo ya registrado
        ↓
Mostrar mensaje
        ↓
No crear cuenta
Nickname ocupado
Nickname ocupado
        ↓
Mostrar mensaje
        ↓
Solicitar otro nickname
Contraseña inválida
Contraseña no cumple requisitos
        ↓
Mostrar requisitos
        ↓
No crear cuenta
Resultado
Usuario registrado correctamente.
Criterios de aceptación
El correo debe ser único.
El nickname debe ser único.
La contraseña debe almacenarse mediante hash.
El sistema no debe exponer información sensible.
El usuario debe recibir una confirmación.
La cuenta debe quedar asociada inicialmente al rol PLAYER.
CU-02 — Iniciar sesión
Actor principal
PLAYER.
Objetivo
Acceder a su cuenta.
Flujo principal
1. Usuario accede al login.
2. Ingresa correo.
3. Ingresa contraseña.
4. Envía formulario.
5. Sistema valida credenciales.
6. Sistema autentica usuario.
7. Sistema crea sesión.
8. Usuario es redirigido a la plataforma.
Flujos alternativos
Credenciales incorrectas
Credenciales inválidas
        ↓
Mostrar mensaje
        ↓
No iniciar sesión
Cuenta bloqueada
Usuario bloqueado
        ↓
Denegar acceso
        ↓
Mostrar información correspondiente
Criterios de aceptación
Las rutas protegidas deben requerir autenticación.
La autorización debe validarse en backend.
La sesión debe poder finalizar.
Las credenciales nunca deben almacenarse en texto plano.
CU-03 — Gestionar perfil
Actor principal
PLAYER.
Objetivo
Actualizar su identidad dentro de la plataforma.
Flujo principal
1. Usuario accede a su perfil.
2. Modifica información.
3. Guarda cambios.
4. Sistema valida información.
5. Sistema actualiza perfil.
6. Usuario visualiza cambios.
Datos editables
Nombre visible.
Avatar.
Biografía.
País.
Ciudad.
Restricción
El nickname no podrá modificarse inicialmente desde el perfil durante el MVP.
Esto podrá modificarse posteriormente.
Criterios de aceptación
Un usuario solo puede editar su propio perfil.
Los datos deben validarse.
La actualización debe ser inmediata después de guardarse.
CU-04 — Crear equipo
Actor principal
PLAYER.
Objetivo
Crear un equipo para participar en torneos.
Precondiciones
Usuario autenticado.
El usuario no debe estar bloqueado.
Flujo principal
1. Usuario accede a "Mis equipos".
2. Selecciona "Crear equipo".
3. Ingresa nombre.
4. Ingresa tag.
5. Envía formulario.
6. Sistema valida datos.
7. Sistema crea equipo.
8. Sistema asigna al usuario como capitán.
Resultado
Equipo creado correctamente.
Criterios de aceptación
El creador debe quedar como CAPTAIN.
El nombre debe cumplir las reglas establecidas.
El tag debe cumplir las reglas establecidas.
El sistema debe impedir inconsistencias de membresía.

5. AJUSTES TÉCNICOS APLICADOS
5.1 Idempotencia
Las operaciones críticas deben ser idempotentes.
Ejemplo:
Confirmar resultado
        ↓
Si ya está confirmado
        ↓
No volver a avanzar ganador
Esto evita errores por:
Doble clic.
Reintentos.
Peticiones duplicadas.
5.2 Transacciones
Deben utilizarse transacciones en:
Confirmación de inscripción.
Generación de bracket.
Confirmación de resultados.
Avance automático.
Finalización del torneo.
Actualización de rankings.
5.3 Bloqueo de operaciones críticas
Para evitar condiciones de carrera, operaciones como:
INSCRIPCIÓN
CONFIRMACIÓN DE RESULTADO
ASIGNACIÓN DEL GANADOR
deben protegerse contra modificaciones simultáneas.
5.4 Auditoría
Las acciones administrativas deben registrar:

Acción.
Entidad.
Estado anterior.
Estado nuevo.
Fecha.
5.5 Separación de responsabilidades
La lógica debe mantenerse así:
CONTROLLER
    ↓
SERVICE
    ↓
DOMAIN LOGIC
    ↓
REPOSITORY
Los controladores no deben contener reglas complejas.

3. REQUISITOS FUNCIONALES
RF-01 — Registro de usuarios
El sistema debe permitir a un visitante crear una cuenta.
Datos mínimos:
Correo electrónico.
Contraseña.
Nickname.
El sistema debe validar:
Formato del correo.
Unicidad del correo.
Unicidad del nickname.
Seguridad mínima de la contraseña.
Futuro
El modelo deberá permitir posteriormente:
Registro con Google.
Registro con Discord.
Registro con Twitch.
Registro con otras plataformas.
RF-02 — Inicio de sesión
El sistema debe permitir que un usuario autenticado acceda a su cuenta mediante:
Correo electrónico.
Contraseña.
El sistema debe:
Generar una sesión autenticada.
Controlar el acceso según el rol.
Permitir cerrar sesión.
Permitir renovar credenciales.
Futuro
Autenticación multifactor.
Passkeys.
Inicio de sesión social.
RF-03 — Recuperación de contraseña
El sistema debe permitir solicitar la recuperación de una contraseña mediante correo electrónico.
El enlace o token de recuperación debe:
Ser temporal.
Tener un único uso.
Ser invalidado después de restablecer la contraseña.
RF-04 — Gestión del perfil
El usuario debe poder visualizar y editar:
Nickname.
Nombre visible.
Avatar.
Biografía.
País.
Ciudad.
El sistema debe mostrar:
Torneos jugados.
Victorias.
Derrotas.
Puntos.
Posición en ranking.
Futuro
Enlaces sociales.
Perfil competitivo público.
Insignias.
Logros.
Estadísticas avanzadas.
RF-05 — Gestión de roles
El sistema debe gestionar inicialmente los siguientes roles:
PLAYER
MODERATOR
ADMIN
El sistema debe impedir que un usuario realice acciones sin autorización.
Futuro
El modelo debe permitir:
SUPER_ADMIN
TOURNAMENT_ADMIN
SUPPORT
FINANCE
CASTER
Por este motivo, se recomienda un sistema basado en roles y permisos, en lugar de codificar permisos directamente en la lógica.
RF-06 — Gestión de videojuegos
El administrador debe poder:
Crear videojuegos.
Editar videojuegos.
Activar videojuegos.
Desactivar videojuegos.
Gestionar modalidades.
Ejemplo:
Valorant
   ├── 1v1
   ├── 2v2
   └── 5v5
Un videojuego desactivado no debe poder utilizarse para crear nuevos torneos.
RF-07 — Solicitud de torneo
Un jugador autenticado debe poder solicitar un futuro torneo.
La solicitud debe contener:
Videojuego.
Modalidad.
Formato deseado.
Fecha preferida.
Horario preferido.
Comentario opcional.
El sistema debe registrar:
Usuario solicitante.
Fecha de creación.
Estado de la solicitud.
Restricción
El usuario no crea directamente un torneo.
Solo genera una solicitud.
RF-08 — Votación de solicitudes
Un usuario autenticado debe poder apoyar una solicitud existente.
Reglas:
Un usuario solo puede votar una vez por solicitud.
Un usuario puede retirar su voto.
No puede votar solicitudes cerradas.
El sistema debe mostrar la demanda total.
Futuro
Votaciones por fecha.
Votaciones por horario.
Sugerencias inteligentes.
Detección automática de solicitudes similares.
RF-09 — Gestión de equipos
Un jugador debe poder:
Crear un equipo.
Editar la información básica.
Invitar jugadores.
Expulsar jugadores.
Abandonar un equipo.
Cambiar el capitán.
El equipo debe contener:
Nombre.
Tag.
Logo.
Capitán.
Estado.
Restricción
El sistema debe impedir la existencia de dos miembros activos iguales dentro del mismo equipo.
Decisión técnica

1. VISIÓN GENERAL DEL PROYECTO
1.1 Nombre del producto
TopRival
1.2 Concepto
TopRival es una plataforma web de competencias gamer que permite a los jugadores descubrir, solicitar e inscribirse en torneos oficiales organizados y gestionados directamente por la plataforma.
A diferencia de plataformas abiertas en las que cualquier usuario puede crear un torneo, en TopRival la creación, configuración, administración y monetización de los torneos estará centralizada en el equipo administrativo de la plataforma.
La comunidad tendrá un papel activo en la toma de decisiones mediante un sistema de solicitudes y votaciones de futuros torneos.
1.3 Visión
Convertirse en una de las principales plataformas de competencias gamer de Latinoamérica, conectando jugadores con torneos profesionales, organizados y basados en la demanda real de la comunidad.
1.4 Misión
Ofrecer una experiencia competitiva gamer confiable y accesible mediante la organización centralizada de torneos, sistemas automatizados de competición, rankings y participación activa de la comunidad.
2. PROPUESTA DE VALOR
2.1 Propuesta central
TopRival permite a los gamers competir en torneos oficiales, organizados profesionalmente y creados teniendo en cuenta los intereses reales de la comunidad.
La plataforma se encarga de:
Crear torneos.
Definir reglas.
Gestionar inscripciones.
Gestionar pagos.
Crear brackets.
Administrar partidos.
Validar resultados.
Resolver conflictos.
Actualizar rankings.
Gestionar premios.
Los jugadores pueden:
Descubrir torneos.
Inscribirse.
Crear o gestionar equipos.
Competir.
Consultar brackets.
Reportar resultados.
Consultar rankings.
Solicitar futuros torneos.
Votar por solicitudes de la comunidad.

9. REGLAS DE NEGOCIO PRINCIPALES
RN-01 — Creación de torneos
Solo los usuarios con permisos administrativos pueden crear torneos.
RN-02 — Publicación
Un torneo no será visible públicamente hasta tener el estado PUBLISHED.
RN-03 — Participación
Un jugador solamente puede participar si cumple los requisitos definidos por el torneo.
RN-04 — Equipos
Un usuario no puede pertenecer al mismo equipo más de una vez.
RN-05 — Inscripciones
Un jugador o equipo no puede inscribirse más de una vez al mismo torneo.
RN-06 — Pago
Cuando un torneo sea pago, la inscripción no estará confirmada hasta que el pago sea validado.
RN-07 — Generación de bracket
El bracket solo podrá generarse cuando:
Las inscripciones estén cerradas.
Los participantes estén confirmados.
El administrador autorice la generación.
RN-08 — Resultado
Un resultado deberá ser confirmado o validado antes de modificar oficialmente el bracket.
RN-09 — Disputas
Una disputa impedirá el avance automático hasta ser resuelta.
RN-10 — Solicitudes
Un usuario podrá solicitar torneos, pero no crearlos directamente.
RN-11 — Votaciones
Un usuario solo podrá votar una vez por una misma solicitud.

33. Regla UX fundamental de TopRival
Hay una decisión que recomiendo adoptar como principio de diseño:
El usuario nunca debería tener que entender la máquina de estados interna. Debe entender qué puede hacer ahora.
Por ejemplo, en lugar de mostrar:
TOURNAMENT_STATUS = REGISTRATION_CLOSED
mostrar:
🔒 Inscripciones cerradas
El torneo comenzará el 15 de septiembre a las 7:00 PM.
En lugar de:
MATCH_STATUS = RESULT_PENDING
mostrar:
🟡 Resultado en revisión
Estamos esperando la confirmación del resultado.
Y en lugar de:
MATCH.COMPLETION_TYPE = BYE
mostrar:
🟢 Avanzas automáticamente
Tu rival no fue asignado en esta ronda.
Esto hará que TopRival se sienta como una plataforma profesional y no como un sistema administrativo.
El siguiente paso
Con esto ya tenemos prácticamente todo el UX Information Architecture:
ER → Arquitectura → API → Estados → Navegación → Pantallas.
Ahora sí recomiendo pasar al Wireframe UX de TopRival, pero hacerlo pantalla por pantalla, empezando por el flujo más importante:
HOME
 ↓
TORNEOS
 ↓
DETALLE DEL TORNEO
 ↓
INSCRIPCIÓN
 ↓
CONFIRMACIÓN
 ↓
DASHBOARD
 ↓
TORNEO
 ↓
BRACKET
 ↓
MATCH
 ↓
RESULTADO
 ↓
CAMPEÓN
Ese flujo representa el core de negocio de TopRival y debería ser el primer wireframe que diseñemos antes de entrar a las pantallas secundarias.
